Many requirements are written as promises: “if the user is an admin, then they may delete the record.” Logic captures this pattern with the implication P → Q, read “P implies Q” or “if P then Q”.

The truth table of P → Q

P  Q | P → Q
T  T |   T
T  F |   F
F  T |   T
F  F |   T

The implication is false in exactly one row: the premise P is true but the conclusion Q is false. That is a broken promise. In every other row the promise was either kept, or it was never triggered.

Why “false premise” gives true

If P is false the promise says nothing about Q, so it cannot be broken. Logicians call this vacuous truth. A contract “if it rains, the picnic is cancelled” is not violated on a sunny day, whatever happens to the picnic.

Contracts in software

  • A precondition is the premise a function assumes.
  • A postcondition is the conclusion the function guarantees.
  • A guard clause checks the premise early and exits, so the rest of the function can rely on it.

Related statements

From P → Q we can form the converse Q → P and the contrapositive ¬Q → ¬P. The converse is a different claim. The contrapositive says the same thing as the original and is often easier to test.

Key idea: an implication fails only when the premise is true and the conclusion is false.
