Real conditions accumulate over time: one developer adds a check, another adds a slightly different one, and soon the same test appears twice. Applying several laws in a row cleans this up without changing behaviour.

The expression

Simplify (P ∧ ¬Q) ∨ (P ∧ Q). It says: “P holds and Q is false, or P holds and Q is true.” Intuitively, that just means “P holds”, and Q does not matter. Let us prove it using laws.

Three steps

  1. Distributive law. P appears in both branches, so factor it out: P ∧ (¬Q ∨ Q).
  2. Complement law. A statement OR its negation is always true, so ¬Q ∨ Q becomes T: P ∧ T.
  3. Identity law. ANDing with true changes nothing: P.

Strategy

  • Look for a shared factor between branches and pull it out.
  • Look for a variable meeting its own negation (P ∨ ¬P or P ∧ ¬P).
  • Finish by removing constants with the identity laws.
  • Verify the result with a quick truth table. If it disagrees, one of the steps was wrong.

In code

// before
if ((isPaid && !isRefunded) || (isPaid && isRefunded)) { ship(); }
// after
if (isPaid) { ship(); }
Key idea: simplification is a chain of small, justified steps, each one an equivalence law.

In the activity, choose the right law for each step and reach the single variable.
